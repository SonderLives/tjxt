## 链路追踪：go-zero 内置 OTel + Jaeger
- 用户要求做链路追踪（Jaeger）。核实 go-zero v1.10.3：
  - `core/service/serviceconf.go:67` 在 `ServiceConf` 初始化时自动 `trace.StartAgent(sc.Telemetry)`；`Telemetry` 字段是 `trace.Config{Name,Endpoint,Sampler,Batcher,...}`，zrpc.RpcServerConf 与 rest.RestConf 都内嵌 `ServiceConf` → **api 与 rpc 配置都支持 Telemetry，且零代码改动自动生效**。
  - **关键坑：v1.10.3 的 `Batcher` 选项是 `zipkin|otlpgrpc|otlphttp|file`，没有 `jaeger`！** 指向 Jaeger 必须用 OTLP：选 `otlphttp` + `Endpoint: 127.0.0.1:4318`（Jaeger OTLP HTTP，默认路径 `/v1/traces`），或 `otlpgrpc` + `4317`。本次用 `otlphttp`+`4318`。`Sampler: 1.0` 全采样（开发用，生产应调低）。`Name` 留空时框架默认取服务 `Name`。
- 落地改动：
  - `docker-compose.yml` 新增 `jaeger` 服务（`jaegertracing/all-in-one:1.57`，`COLLECTOR_OTLP_ENABLED: "true"`，暴露 16686 UI / 4317 gRPC / 4318 HTTP）。
  - 26 个 `apps/**/etc/*.yaml`（13 服务 × api+rpc）批量注入 `Telemetry{Name,Endpoint:127.0.0.1:4318,Sampler:1.0,Batcher:otlphttp}`，Name 取各 yaml 自身 `Name`。
  - 幂等：脚本先 `strip_existing_telemetry` 再注入；`Endpoint` 用 `127.0.0.1`（与 etcd/es/mq 一致的本机约定，因 Go 服务本机跑、依赖 docker 化基建）。
- 坑：用 bash heredoc 跑 Python 注入时，`'\n'` 被写成字面 `\n`（文件里出现 `Telemetry:/n  Name:` 导致 YAML 报 `mapping values are not allowed here`）。**正确做法是用 Write 工具写 .py 脚本文件再 `python file.py` 执行**（heredoc 的 `\n` 转义在 git-bash 下不可靠）。已修复并 PyYAML 校验 26 个全部 parse 通过。
- 使用：`docker compose up -d jaeger`（或 `docker run -d jaegertracing/all-in-one:1.57`），重启各服务（Telemetry 仅在自身 yaml 生效，需每个服务都配），访问 http://127.0.0.1:16686 看调用链。注意 go-zero 的 trace 默认只在跨服务 gRPC 调用产生 span，纯本地逻辑不会产生 span。

## 性能监控 Prometheus（用户选择「只加 Prometheus，暂不做 Loki」）
- 核实 go-zero v1.10.3：Prometheus 是 `ServiceConf` 原生能力（core/service/serviceconf.go 自动 `prometheus.StartAgent`），**配置驱动、零代码**。致命点：core/prometheus/agent.go 在 `c.Host==""` 时直接 return 不启动 → 必须显式设 `Host`（本项目 `0.0.0.0`）。`Port` 默认 9101、`Path` 默认 `/metrics`。
- 落地改动：

  - `docker-compose.yml` 新增 `prometheus` 服务：`prom/prometheus:v2.53.1`，`9090:9090`，`extra_hosts: host.docker.internal:host-gateway`，挂载 `./deploy/prometheus/prometheus.yml:ro`。
  - 新建 `deploy/prometheus/prometheus.yml`：scrape_configs 含 `tjxt-rpc`(9101–9113)、`tjxt-api`(9201–9213)、`prometheus`(自身) 三个 job，target 用 `host.docker.internal:<port>`（因 Go 服务本机跑、Prometheus 跑 docker，metrics 绑 0.0.0.0 故可达）。
- Loki 未做（v1.10.3 无原生 Loki writer，需自定义 logx writer，本期跳过）。
- 验证：`go build ./...` 在 course/api 与 course/rpc 通过（配置字段是 go-zero 标准 `ServiceConf.Prometheus`，编译即确认接线正确）。

- 按建议接入 collector（仅接管 trace，metrics 仍 Prometheus 直拉，logs 未接 Loki）：
  - 新增 `deploy/otel-collector/config.yaml`：otlp receiver(grpc 4317 + http 4318) → batch → otlphttp exporter 到 `jaeger:4318`；仅 traces 管线，metrics/logs 留扩展注释。
  - 改 `docker-compose.yml`：jaeger 去掉 4317/4318 的 host 映射（仅留 16686 UI）；新增 `otel-collector`（`otel/opentelemetry-collector-contrib:latest`，`--config=/etc/otelcol-contrib/config.yaml`，ports 4317/4318/13133，挂载 config，depends_on jaeger）。
  - **关键技巧**：宿主机 4318 从 jaeger 让位给 collector，26 个服务 yaml 的 `Telemetry.Endpoint: 127.0.0.1:4318` **无需改动**（go-zero 仍发到 127.0.0.1:4318，现由 collector 容器应答）。
  - 链路变：go-zero(otlphttp) → 127.0.0.1:4318(collector) → jaeger:4318(内网) → Jaeger UI 16686。
- 验证：docker-compose.yml 与 collector config 均 PyYAML parse 通过；collector 服务名 `jaeger` 在 compose 网络可达。
