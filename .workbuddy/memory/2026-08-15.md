## 链路追踪：go-zero 内置 OTel + Jaeger
- 用户要求做链路追踪（Jaeger）。核实 go-zero v1.10.3：
  - `core/service/serviceconf.go:67` 在 `ServiceConf` 初始化时自动 `trace.StartAgent(sc.Telemetry)`；`Telemetry` 字段是 `trace.Config{Name,Endpoint,Sampler,Batcher,...}`，zrpc.RpcServerConf 与 rest.RestConf 都内嵌 `ServiceConf` → **api 与 rpc 配置都支持 Telemetry，且零代码改动自动生效**。
  - **关键坑：v1.10.3 的 `Batcher` 选项是 `zipkin|otlpgrpc|otlphttp|file`，没有 `jaeger`！** 指向 Jaeger 必须用 OTLP：选 `otlphttp` + `Endpoint: 127.0.0.1:4318`（Jaeger OTLP HTTP，默认路径 `/v1/traces`），或 `otlpgrpc` + `4317`。本次用 `otlphttp`+`4318`。`Sampler: 1.0` 全采样（开发用，生产应调低）。`Name` 留空时框架默认取服务 `Name`。
- 落地改动：
  - `docker-compose.yml` 新增 `jaeger` 服务（`jaegertracing/all-in-one:1.57`，`COLLECTOR_OTLP_ENABLED: "true"`，暴露 16686 UI / 4317 gRPC / 4318 HTTP）。
  - 26 个 `apps/**/etc/*.yaml`（13 服务 × api+rpc）批量注入 `Telemetry{Name,Endpoint:127.0.0.1:4318,Sampler:1.0,Batcher:otlphttp}`，Name 取各 yaml 自身 `Name`。
  - 幂等：脚本先 `strip_existing_telemetry` 再注入；`Endpoint` 用 `127.0.0.1`（与 etcd/es/mq 一致的本机约定，因 Go 服务本机跑、依赖 docker 化基建）。
- 坑：用 bash heredoc 跑 Python 注入时，`'\n'` 被写成字面 `\n`（文件里出现 `Telemetry:/n  Name:` 导致 YAML 报 `mapping values are not allowed here`）。**正确做法是用 Write 工具写 .py 脚本文件再 `python file.py` 执行**（heredoc 的 `\n` 转义在 git-bash 下不可靠）。已修复并 PyYAML 校验 26 个全部 parse 通过。
- 使用：`docker compose up -d jaeger`（或 `docker run -d jaegertracing/all-in-one:1.57`），重启各服务（Telemetry 仅在自身 yaml 生效，需每个服务都配），访问 http://127.0.0.1:16686 看调用链。注意 go-zero 的 trace 默认只在跨服务 gRPC 调用产生 span，纯本地逻辑不会产生 span。

## 日志接入 Loki，也走 collector（用户「现在帮我接入loki 日志存储，这个也要走collector」）
- 背景：go-zero v1.10.3 无 Loki/OTLP logs 导出，只能 console/file 原生日志。采用「文件采集」零业务代码方案：
  - go-zero 写 JSON 文件日志，collector `filelog` receiver 读文件 → `loki` exporter 推给 Loki。
- 26 个服务 yaml 注入 `Log{Mode:file,Encoding:json,Path:D:/code/go/tjxt/logs/<svc>,Level:info}`（<svc> 唯一，如 user-rpc/course-api）；脚本 `fix_log.py`（Write 工具写，复用 fix_prom.py 模式，PyYAML 校验）。go-zero file 模式写 `Path/{access,error,slow,stat,severe}.log`，JSON 字段固定 @timestamp/level/content（无 service、无 caller），服务名只能从目录来。
- collector `deploy/otel-collector/config.yaml` 加 `filelog` receiver（include /var/log/tjxt/**/*.log，operators: json_parser→timestamp→severity→move content→body→regex_parser 取 service）+ `transform/logsvc` 把 service/level 提升为 resource 属性 + `loki` exporter（http://loki:3100/loki/api/v1/push，labels [service.name,level]）+ `logs` 管线 `receivers:[otlp,filelog] processors:[transform/logsvc,batch] exporters:[loki]`。
- 新增 `deploy/loki/loki-config.yaml`（`grafana/loki:latest` 单实例最小配置，filesystem+inmemory ring，auth_enabled:false）。
- `docker-compose.yml`：新增 `loki` 服务(3100)；`otel-collector` 加 `./logs:/var/log/tjxt:ro` 挂载 + `depends_on:[jaeger,loki]`；注释更新为 trace+metrics+logs 三支柱。
- 校验：3 份 YAML 均 PyYAML parse 通过；Docker 不在本 shell PATH，用户本地 `docker compose up -d loki otel-collector` 后查 Loki 流 `{service_name="user-rpc"}`。

## 日志路径改相对（用户「D:/code/go/tjxt/logs/... 能设相对位置吗」）
- go-zero `Log.Path` 支持相对路径（默认 `logs`，相对进程 CWD）；但 v1.10.3 config **不支持 `${ENV}` 占位**（`config_test.go` 断言 `${FOO}` 原样保留），故绝对路径无法靠环境变量参数化。
- 用户确认从仓库根启动服务（CWD=仓库根）。将 26 个 etc yaml 的 `Path: D:/code/go/tjxt/logs/<svc>` 改为相对 `Path: logs/<svc>`（脚本 `fix_log_rel.py` 正则替换 + PyYAML 校验）。CWD=仓库根时落到 `<repo>/logs/<svc>`，与 docker 挂载 `./logs` 对齐，跨机器/系统可移植。
- 同步把 `Makefile` 22 个 `run-<svc>`/`run-<svc>-rpc` 从 `Set-Location apps/<svc>/...; go run . -f etc/x.yaml` 改为从仓库根 `go run ./apps/<svc>/... -f apps/<svc>/.../etc/x.yaml`（脚本 `fix_makefile_run.py`），避免 `make run-<svc>` 在各自服务目录启动导致日志散落、collector 采不到。
- 踩坑：第一次 `fix_makefile_run.py` 正则把 `$(GO)` 错写成 `\$\{GO\}`（应为 `\$\(GO\)`），0 匹配；改用宽松 `.*` 模式后正常。
