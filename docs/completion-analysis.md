## 3. 各模块功能完备度详细说明

**基础域**
- **auth**：JWT 鉴权、登录、权限校验完整；19 个 RPC 覆盖 token 签发/校验/刷新等。
- **user**：用户/详情 CRUD、资料查询完整；无外部依赖，作为基础服务独立运行。

**内容域**
- **course**：38 个 API / 38 个 RPC 全实现（分类、讲师、课程上架、目录等）。代码注释标明**教师姓名/头像（来自 user 服务）与课时（来自 learning 服务）当前未接线**，属有意桩。
- **media**：文件/媒资 CRUD、上传签名、播放/预览签名均实现；但对象存储后端为 **mock**（`mockBaseURL = http://127.0.0.1:9000`），未接真实 COS/OSS。逻辑真实，仅存储后端待替换。
- **learning**：学习记录提交/查询完整；注释标明 `section_type` 字段目前被忽略（占位映射）。
- **exam**：题库/试卷/答题逻辑完整。
- **search**：课程搜索 API/RPC 完整，依赖 course RPC 获取课程数据。

**交易域**
- **trade**：购物车、订单、退款全实现；依赖 pay + course RPC。**优惠券/促销未接入**（注释：「优惠券暂未接入，实付金额等于课程价格之和」）。通过 RabbitMQ 发布领域事件，Producer 优雅降级（MQ 不可用时为 nil，不阻塞启动）。
- **pay**：支付下单、回调、对账逻辑完整；注释标明支付回调 URL 为 **demo 占位**，未接真实支付网关。
- **promotion**：优惠/活动逻辑完整，但当前无服务调用它（待 trade 接线）。

**运营域**
- **message**：站内信/通知完整。
- **remark**：评价/点赞完整。
- **data**：看板数据（board/today/top10）读写完整；真实模块编译通过。

## 5. 服务间通信与依赖关系

### 5.1 已接线的 RPC 依赖（编译通过，zrpc 客户端已实例化）

| 调用方 | 依赖（跨服务 RPC） | 层级 |
|--------|-------------------|------|
| trade (rpc) | → course, pay | RPC→RPC |
| search (rpc) | → course | RPC→RPC |
| learning (api) | → course | API→RPC |

### 5.2 代码注释标明「应有但尚未接线」的集成

| 期望依赖 | 现状 | 说明 |
|----------|------|------|
| course → user | 未接线 | 教师姓名/头像来自 user 服务，course 侧未接入 user 客户端 |
| course → learning | 未接线 | 课时 lesson_id 属 learning 服务，当前填 0 |
| trade → promotion | 未接线 | 优惠券暂未接入，实付金额未扣减优惠 |
| pay → 真实支付网关 | 占位 | demo URL，非真实渠道回调 |

### 5.3 事件驱动（异步）
- **trade** 通过 **RabbitMQ** 发布领域事件（如订单创建），Producer 在 MQ 不可用时优雅降级为 nil，**不阻塞服务启动**。这是合理的异步解耦设计。

### 5.4 依赖健康度评估
- **已接线的依赖**：结构健全——客户端在 `ServiceContext` 中实例化、配置项存在、编译通过。
- **未接线的依赖**：属「按设计分阶段集成」范畴，已在代码中明确标注，非缺陷；但意味着跨域数据（教师、课时、优惠）目前不完整。
- **独立性过强**：user / auth / media / promotion / message / remark / exam / data 当前**无任何出向 RPC 依赖**，与「微服务应适当组合」的预期相比偏孤立，主要因上述跨服务接线尚未完成。
